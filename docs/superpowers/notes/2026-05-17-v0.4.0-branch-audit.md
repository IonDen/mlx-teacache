# v0.4.0 Branch Audit

**Branch:** `feature/v0.4.0-klein-base-4b`  
**Base:** `main` / `4e75a16`  
**Audit date:** 2026-05-17  
**Scope:** release branch delta for `flux2-klein-base-4b`; only current-release issues, not deferred CFG/base-9B/future-fit work.

## Verdict

The branch is close, but I would fix two release-blocking issues before tagging:

1. the 1.41x speedup is framed as if 3/25 step skips explain it, but that is mathematically impossible without the FLUX.2 `mx.compile`-avoidance effect also contributing;
2. custom user coefficients on `flux2-klein-base-4b` silently inherit the built-in 0.17 threshold even though that threshold was tuned for the bundled polynomial.

A third issue is evidence/reproducibility: the threshold sweep that justifies the new default is referenced from `/tmp`, not committed, and the source comment disagrees with the public 1.41x number.

## Findings

### 1. Performance docs over-attribute the base-4B speedup to step-skipping

**Severity:** High  
**Files:** `README.md`, `CHANGELOG.md`, `ROADMAP.md`, `scripts/bench_speedup.py`

The release repeatedly says `flux2-klein-base-4b` skips 3/25 steps for a 1.41x measured speedup:

- `README.md:104`, `README.md:154`, `README.md:179`
- `CHANGELOG.md:12`, `CHANGELOG.md:15`
- `ROADMAP.md:7`

But 3 skipped steps out of 25 cannot by itself produce 1.41x. Even if skipped steps cost zero and every non-skipped step cost the same, the upper bound from skipping alone is `25 / 22 = 1.14x`; TeaCache skipped steps still run prelude/tail work, so the skip-only bound is lower in practice.

The benchmark compares vanilla mflux against the wrapper path (`scripts/bench_speedup.py:181-198`). For FLUX.2, the wrapper replaces mflux's compiled `_predict` with an eager closure. The README itself documents that FLUX.2 gains can come from `mx.compile` avoidance (`README.md:171-179`, `README.md:193-195`). Therefore the base-4B row should be framed as:

> `mx.compile` avoidance + 3/25 TeaCache step-skips on M1 Max

not just "TeaCache step-skipping". Otherwise users on eager chips, or future mflux/MLX versions where compile is faster, will expect a step-skip speedup that the skip count cannot deliver.

**Fix:** keep the "first FLUX.2 variant where the gate engages" claim, but split attribution:

- table mechanism: `step-skipping + mx.compile avoidance`;
- text: "3/25 skips; measured M1 Max wall-clock speedup 1.41x, which includes FLUX.2 eager-wrapper/compile-avoidance effects";
- if you want a pure algorithmic number, add a control benchmark that compares eager wrapper at threshold 0/no-skip vs eager wrapper at 0.17.

### 2. Custom coefficients silently inherit base-4B's built-in threshold

**Severity:** High  
**Files:** `src/mlx_teacache/api.py`, `src/mlx_teacache/coefficients.py`, `README.md`

`apply_teacache()` resolves `rel_l1_thresh` before resolving coefficients:

- `api.py:181-186` loads built-in provenance and applies `default_thresh=0.17` for `flux2-klein-base-4b`;
- `api.py:192-197` only later switches to `Provenance.for_user_supplied()` when `coefficients` is passed.

That means:

```python
apply_teacache(base4b_flux, coefficients=my_coeffs)
```

uses `rel_l1_thresh=0.17` even though `my_coeffs` did not come from the built-in calibration. The handle then reports `provenance.source == "user"`, while the threshold came from the built-in base-4B provenance. This is especially risky because the registry comment says 0.17 was empirically tuned for the bundled polynomial and has a sharp quality cliff (`coefficients.py:174-184`).

Before this branch, the same call shape used the public default 0.20. The v0.4 behavior is therefore a silent API change for custom coefficients on the new variant.

**Fix:** resolve coefficients/provenance first. If `coefficients is not None` and `rel_l1_thresh` is omitted, use the package fallback 0.20 or require an explicit threshold. If inheriting a variant default for user coefficients is intentional, document that in `README.md:129-133` and expose it clearly in handle metadata.

### 3. The 0.17 threshold evidence is not committed/reproducible

**Severity:** Medium  
**Files:** `CHANGELOG.md`, `docs/calibration.md`, `src/mlx_teacache/coefficients.py`, `scripts/bench_speedup.py`

The new default threshold is load-bearing release behavior, but the evidence path points to local `/tmp` files:

- `CHANGELOG.md:29` cites `/tmp/sweep_thresholds.py`;
- `docs/calibration.md:34` tells future recalibrations to use `/tmp/sweep_thresholds.py`;
- `coefficients.py:174-180` cites `/tmp/sweep_thresholds.py` and `/tmp/sweep_fine.py`.

Those scripts/reports are not committed. The committed `scripts/bench_speedup.py` also does not expose a threshold parameter or SSIM sweep mode, so it cannot reproduce the documented `0.20 -> 19/25 skips, SSIM 0.76` or `0.175 -> 14/25 skips, SSIM 0.78` claims.

There is also a public/private number mismatch: the source comment says 0.17 gives `1.30x` (`coefficients.py:178`), while README/CHANGELOG/ROADMAP say `1.41x`.

**Fix:** commit the sweep script or a compact JSON/Markdown threshold-sweep report under `scripts/` or `docs/`. At minimum, remove `/tmp` references from committed docs and reconcile `1.30x` vs `1.41x`.

## Lower-Severity API Polish

The new sentinel leaks through public introspection:

```text
(flux: 'Any', *, rel_l1_thresh: 'float | Any' = <object object at 0x...>, ...)
```

This is not a runtime blocker, but it undercuts the CHANGELOG claim that the public-facing signature documentation is updated. A small named sentinel with a stable `repr`, or overloads plus a private implementation, would make generated docs and `help()` output less confusing.
